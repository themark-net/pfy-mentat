- **Summary / Key Claims** (upstream README at the pin; their claims, not measured here except the config and ledger contract below): stock Hermes, no patched core, through the public plugin subagent lifecycle API (`ctx.subagent_lifecycle`). You define a roster (for example reviewer, scout, test-writer), each with instructions, toolsets and an optional model, route and reasoning effort. The model only picks a teammate **name**. Six tools: `teammates_roster`, `teammate_assign` (returns a `run_id` at once), `teammate_check`/`teammate_wait`, `teammate_message` (steer mid-run), `teammate_stop`. A teammate's toolsets can only narrow the parent's. `follow_up: true` carries a bounded digest of earlier assignments. Every run goes in a per-profile SQLite ledger (`<HERMES_HOME>/plugin-data/hermes-teammates/data.db`). Optional Kanban `teammates` lane: a card moves to review on success, blocked on failure. Roster in `config.yaml` or a separate `roster_file`.
- **Why it matters here**: on 2026-10-20 Mark chose Hermes as pfy-mentat's bot interface (Entry 134, wiring pending). Our gate is Tester plus Reviewer, and briefs get rewritten for each delegation. A fixed `tester`/`reviewer` roster with narrowed toolsets and a durable ledger is the Hermes-native way to run that loop on nimo, and it needs no patched core.
- **Fit on nimo**: Yes. 8.8 MB of pure Python; the config and ledger modules are stdlib only. A real run needs the isolated Hermes from Entry 134 (`HERMES_HOME` under the worktree `./tmp`, never `~/.hermes`) on a version that has `ctx.subagent_lifecycle` (0.21.4 or newer). `hermes plugins install` writes into the Hermes home, so only run it with the isolated `HERMES_HOME`.
- **Verified on the Grok Bot box** (clone at the pin, system Python 3, bubblewrap 0.12.0 with no network, temp HOME; no Hermes): smoke PASS for the **config and ledger contract only**. A two-teammate roster parsed with no errors; an absent `toolsets` stayed `None` (inherit) and a set one stayed `["file", "terminal"]`. An unknown key (`api_key`), a bad name (`Reviewer!`) and an empty `toolsets` list each made that teammate invalid. 5,000-character instructions were clipped to 4,000 with a warning and stayed launchable. `max_live_runs: 99` fell back to 4 with an error. On a temp SQLite ledger with cap 2 the third run in one session was refused while another session was admitted; `finish()` worked once and refused a second finish; a non-terminal status and an unknown column raised. Clone, temp HOME and `~/.hermes/plugin-data/hermes-teammates` unchanged.
- **Findings**:
  - **Hermes tool search defers plugin tools**: per the README, at the inspected Hermes pins `tools.tool_search.enabled: auto` defers plugin tools whenever any are available, so the model reaches the teammate tools through `tool_search`/`tool_describe`/`tool_call`. Entry 134's follow-up (re-run the bake-off with those meta tools off) touches the same setting. Decide on it before relying on teammates.
  - Settings are read on every call, but the teammate names in the `teammate_assign` description are fixed at start-up: a new teammate works by name at once, and only shows in the description after a restart.
  - Completion notices are reserved (`notify_on_completion` does nothing on current Hermes). Poll with `teammate_wait`.
  - Token receipts need the `subagent_start` and `post_api_request` hooks in-process and don't survive restarts.
