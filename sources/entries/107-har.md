- **Summary / Key Claims** (upstream README and `har --help`): "The open harness for AI coding workflows you can trust and verify." A repo gets a machine-readable `.har/` contract (`stages.json`, `harness.env`, stage scripts) that Claude Code, Cursor, Codex or any MCP agent reads the same way. `har env launch <id>` makes a per-slot git worktree on its own branch (own ports and, if configured, own DB via Docker), `har env verify <id> --full` runs the repo's `verificationStages` (scaffold default: typecheck, unit-tests, lint, readiness) and records the result against the exact tree, `har env complete` reuses the last matching full validation and keeps the branch for a PR, `har hooks` is a commit gate that blocks unverified change batches, `har env maintain` diffs the harness against current templates, `har mcp` is a stdio MCP server, and `har control` runs the Mission Control dashboard locally (needs Docker). There is also `har hq`, a hosted portal (`app.harhq.com`), and `har telemetry`, which is on by default.
- **Fit on nimo**: Node CLI, no GPU, no model of its own, so resource-wise trivial on nimo (AMD Strix Halo, 128 GB total, ~107 GB visible to Linux, no NVIDIA). It does not call a model; the agent in the slot would be whatever we already run (headless Grok Build, or a local-Ollama lane with `qwen3.6:35b`), so no new key. Two layout problems to solve before any nimo run: (1) session worktrees go to `$HOME/worktrees/` and state to `~/.har/` (outside `~/DEVELOP`), so run it with `HOME` pointed under `~/DEVELOP/pfy-mentat/tmp/` or get Mark's approval; (2) with telemetry on (the default), `har env launch` npm-installs `@osfactory/otel-hook` into `~/.har/otel-hooks` and writes hook entries into `~/.cursor/hooks.json`, `~/.claude/settings.json` and `~/.codex/hooks.json`, with raw prompt capture to a localhost Mission Control endpoint. On nimo that would edit Mark's real Cursor hooks, so `har telemetry off` must run first. Mission Control needs Docker; not checked on nimo.

- **Why it matters here**: Best eval-auto candidate of this slice, against our headless Grok Build `/orchestrator`-in-worktree lane plus Tester/Reviewer gating at a pinned head sha. HAR does the mechanical half of that lane in one tool: one worktree per task off main, the repo's real checks run the same way every time, and a pass tied to the exact tree (our gate pins a commit sha by hand). It would not replace Tester/Reviewer judgment; it could replace our hand-rolled worktree setup and "did the checks really run at this sha" step, and `har mcp` could give Build, Cursor and local lanes the same verify contract.
