### Entry 111: runx — governed runtime for agent skill workflows that seals a local, verifiable receipt for every run (no account)

- **Summary / Key Claims** (upstream README, `docs/getting-started.md`, `runx --help`, the `cli-v0.9.1` tree): "the governed runtime for agent skills ... every act produces a receipt." A skill is a portable `SKILL.md` plus an execution profile (`X.yaml` at v0.9.1; `run.yaml` on main) with runners made of `agent`, `tool`, `operation`, `ask` or `skill` steps. runx "admits each act under explicit authority, delivers credentials without turning them into prompt material, supervises execution, and seals the result into a verifiable receipt"; "there are no agents, prompt chains, model loops, or vector stores here." The local CLI needs "no account and no hosted surface" to seal a receipt; a hosted registry/catalog (runx.ai/x), `runx login`, `runx publish` and provider connectors are optional. Receipts (`runx.receipt.v1`) record issuer, Ed25519 signature, digest, subject, authority (actor, grants, scopes, execution boundary), decisions, acts and seal; `runx verify` checks the receipt tree and `runx history` lists it. CLI tools are "intentional trusted local executables under an exact resolved grant ... it does not claim portable OS confinement."
- **Signing caveat (read on the box)**: With no key configured, receipts are signed by a placeholder local identity (`issuer.kid` `runtime-skeleton`) and `runx verify` refuses them unless `--allow-local-development-signatures` is passed. Real signatures need `RUNX_RECEIPT_SIGN_KID`, `RUNX_RECEIPT_SIGN_ED25519_SEED_BASE64` and `RUNX_RECEIPT_SIGN_ISSUER_TYPE` (`hosted` or `ci`; "production receipts are never stamped as local issuers") set together; a locally generated seed is enough, no account. By default receipts go to `.runx/receipts` in the working directory; `-R` / `--receipt-dir` moves them.
- **Fit on nimo**: One static musl binary (`runx`, ~30 MB, plus `runx-js-worker`) that can live under `~/DEVELOP/pfy-mentat/tmp/runx/`; the hello-world runner needs `node` (nimo's or a tarball under `tmp/`). No GPU, no model for the local path. **Do not use `curl -fsSL https://runx.ai/install | sh` or `npm i -g @runxhq/cli` on nimo** (both install outside `~/DEVELOP`). The binary also carries the hosted API (`api.runx.ai`), login, publish and x402 payment schemas; none of that is needed or used here, and nothing should be published or paid for.
- **Verified on the Grok Bot box** (`/tmp`, temp HOME): the `runx-0.9.1-x86_64-unknown-linux-musl.tar.gz` sha256 (`59eee2af81d24d0f8ba2416e2bac55d147ed93693e6a41ffe7c2cfd5cba98cc7`) matched the upstream `.sha256` asset; the `runx` binary inside is `e0c0627882c2ce7a4e8cfb20cf4896a4aa371db0e13c95c8b86fa31276388b60`; `--version` prints `runx-cli 0.9.1`. The upstream `examples/hello-world` (clone at `cli-v0.9.1`) ran with `runx skill ./examples/hello-world -i message=... --json` and returned `runx.skill_run.v1` with `status: sealed` and a `receipt_id`; with no key, `runx verify` refused the receipt as above and passed with `--allow-local-development-signatures`. With a throwaway Ed25519 seed (issuer type `ci`), `runx verify --receipt-dir` reported the receipt `valid` in `production` signature mode; a different seed gave `SignatureKeyHashMismatch`, and an edited `created_at` gave `SealDigestMismatch` + `SignatureInvalid` (both `valid: false`, exit 3). The smoke below PASSed under bubblewrap (read-only root, no network), without bwrap, and under `unshare -rn`; it exits 2 with no binary, no example clone (or a `main` clone, whose layout differs), or a wrong `$RUNX_SHA256`. Not verified: graphs, agent steps, credentials, connectors, `runx harness`, MCP serve, hosted verification, approval gates.
- **Why it matters here**: Pattern reference for recording what a pfy skill run did and under what authority. Today a Build drop-in or loop-skill run leaves a git branch, a handoff doc and maybe a PR comment; nothing ties "this skill, these inputs, this grant, this exit" into one checkable record. runx's receipt shape (subject, authority with grants and execution boundary, decisions, acts, seal, lineage) and its fail-closed verify (refuse placeholder signatures by default) are worth copying into a small pfy receipt for `./pfy` skill runs. No eval-auto trial: runx would be a second skill format and runtime beside our skill packs, and it does not sandbox CLI tools.

- **How this fails / how we recover**:

| Risk | How it fails | Recovery |
|------|----------------|----------|
| Placeholder signatures read as proof | Default receipts use the `runtime-skeleton` identity | Smoke and any trial use a real (throwaway or kept) seed; never `--allow-local-development-signatures` as evidence |
| Hosted creep | Login, publish, registry or payments get used | Non-goals; nothing hosted in a trial; no account |
| Not a sandbox | A CLI-tool step runs with the user's rights | Treat runx as a record, not isolation; pair with a worktree or VM (see Entry 109) |
| Format churn | `X.yaml` (v0.9.1) vs `run.yaml` (main) | Binary sha and example tag pinned together; smoke exits 2 on a main clone |
| Receipts in the repo | `.runx/receipts` lands in the working dir | Smoke passes `-R` to the scratch dir |
