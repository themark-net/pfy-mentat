### Entry 136: Harness² (harness2): Google Research framework that tunes an agent's harness per task (Propose-Probe-Compose) and keeps the lessons

- **URL**: https://github.com/google-research/harness2 (Apache-2.0, Python 3.12/3.13; 12,752 stars and 1,176 forks at this read; no release, `pyproject` version 0.1.0; checked at commit `1cfe254e8d25`, 2026-10-13, 3 commits in total: the 2026-10-08 open-source drop `e0fb65029fee` and 2 after it). Paper: https://arxiv.org/abs/2610.14224 (Xu et al., Google, submitted 2026-10-09). Site: https://harness2.github.io. "Not an officially supported Google product."
- **Date**: 2026-10-19 (requested intake, outside the daily X window)
- **Source / Poster**: requested by Mark in chat on 2026-10-19 (no X post)
- **Summary / Key Claims** (README and docs at `1cfe254e8d25`, paper abstract): a harness is everything around a model (prompts, tools, memory, skills, orchestration). Harness² changes the harness, not the weights, and works at two levels. **Task level**: on a new task with no ground-truth checker, an editor proposes edits to eight parts of the harness (system prompt, guardrails, memory, tool guidance, subagents, skills, scripts, plugins), probes each on the same task, and composes a refined harness from how the runs differed. `--k` sets the budget, either as `parallel` (k general plus k domain candidates, then k compositions) or `sequential` (k steps in a row). **Harnessing level**: after each task it saves the adopted harness and lessons backed by evidence in a library that guides later tasks. Executors are OpenCode (default) or Codex. Benchmarks are JobBench, LAB (legal work) and WorkBuddy-Bench (Tencent; office, web and code). One step improved GLM-5 and Gemini 3.5 Flash over their base harnesses by up to 11.5 points on WorkBuddy, 4.5 on JobBench and 11.8 pp partial pass on LAB.
- **Why it matters here**: it is the research version of what we do by hand. Bots and Build sessions learn rules, we write them into `AGENTS.md`, skills and guardrails, and Tester catches the misses. Harness² measures each harness edit against the same task before keeping it, and builds a library of what worked. For pfy-mentat the useful part is the method: test edits to our Build drop-ins and skills on one task before adopting them. It is not a new runtime for the bots.
- **Overlap with what we catalog**:
  - **JevAgentHarness (131)** routes each step to a strong or fast model and leaves the harness alone. Harness² leaves the model alone and rewrites the harness. They don't conflict: jah could sit in front of the executor's model.
  - **atg-framework (093, 101)** compiles a task into a graph and runs it with repair. That is planning inside one run. Harness² works one level up, on the prompts, skills and guardrails the executor runs with. They could stack, but nothing here connects them.
  - **Harness Score (128)** grades a harness from static files with no runs. Harness² improves a harness from live runs. Harness Score is the cheap check; Harness² is the expensive tuner.
  - **Hermes Agent feedback loops** (TOOLS.md row, `hermes-feedback` skill) and **cass-memory (108)** learn rules from past sessions. Harness²'s library is the same idea, except each lesson must be backed by a contrast between probe runs.
  - It already uses **OpenCode**, which our Hermes bake-off runs as an arm.
- **Fit on nimo**: partly, and not yet proven. The package installs into a venv under `~/DEVELOP/pfy-mentat/tmp/harness2/` (no runtime deps; `[render]` adds openpyxl and python-pptx). `harness2-demo` needs no model, key or network. **Local models**: executor and improver take any OpenCode `provider/model` string. A Vertex check only runs when a model starts with `google-vertex`, so an Ollama or llama.cpp provider in OpenCode's own config should work in principle. The JobBench judge takes any OpenAI-compatible `HARNESS2_JUDGE_BASE_URL` with `HARNESS2_JUDGE_API_KEY` (Ollama ignores the key). But the shipped setup assumes Vertex Gemini and Claude throughout. WorkBuddy setup writes Gemini routes and needs Docker. LAB needs Pandoc and Poppler. The Codex path needs a Responses API endpoint (the bundled bridge is LiteLLM to Vertex). **No paid key is strictly needed for JobBench with local models, but nobody has run it that way yet.** **Cost on nimo is time**: each task is several full agent runs (the demo did 28 executions and 32 editor calls for 2 tasks at `--k 2` in both modes), so one task on `qwen3.6:35b` could take hours.
- **Verified on the Grok Bot box** (clone at `1cfe254e8d25`, `uv venv --python 3.12` plus `uv pip install -e '.[render]'`; bubblewrap 0.12.0, no network, temp HOME): `harness2-demo --k 2` exit 0 in 1.4 s, 2 accounting tasks, 0 failed, 28 executions, 32 editor calls. The library went from 0 entries before task 1 to 1 entry before task 2 in both modes, so the lessons do carry over. Temp HOME stayed empty. Upstream unit tests: 5/5 OK. No benchmark setup, no model.
- **Findings**:
  - **`.env.example` is missing.** The README and SETUP.md say `cp .env.example .env`, but the file is not in the repo at `1cfe254e8d25`. Write `.env` by hand from the SETUP.md table.
  - **Executors run with no network limit, and Codex runs with its sandbox off**, by upstream design. On nimo that needs a container or bwrap and a network allow-list before any real run. Benchmark rubrics are online, so open web access also spoils the scores.
  - **Data licenses differ from the code license.** WorkBuddy-Bench uses a custom Tencent license with an EU limit. Datasets come from Hugging Face under their own terms. Setup clones pinned upstream checkouts and downloads data, so it needs network access.
  - The paper's gains are on GLM-5 and Gemini 3.5 Flash with frontier editors. It doesn't show that a 35B local model can do the editor and composer jobs. That is the open question for us.

- **How this fails / how we recover**:

| Risk | How it fails | Recovery |
|------|----------------|----------|
| Local editor too weak | A 35B improver proposes edits that don't help, so composition just adds noise | Start with `--k 1` on 2-3 tasks; compare with the base harness before trusting it |
| nimo hours | Probe runs multiply wall time per task | `--max-tasks 1`, `--dry-run` first, run when the host is quiet |
| Unsandboxed executor | Agent touches the host or the open web | Container or bwrap, network allow-list, never Codex with the sandbox off on nimo |
| Vertex coupling | WorkBuddy and LAB setup expect Gemini routes | Use JobBench with a local OpenAI-compatible judge first |
| Overfitting harness edits | Lessons fit one benchmark, not our work | Treat the library as suggestions; a person reviews before anything goes into AGENTS.md or skills |

- **Status**: Cataloged I0. Offline demo PASS on the Grok Bot box; not staged on nimo.

**Verdict: catalog-only.** It is a strong, Apache-2.0 method for testing harness edits before keeping them and can in principle run fully local, but the shipped setup is built around Vertex and nothing shows a local 35B model can do the editor job, so it waits for a scoped eval-auto trial (JobBench, `--k 1`, Ollama executor and judge) that Mark approves.
