### Entry 119: AgentDescent — parallel, merge-based self-evolution of skills, prompts and harnesses ("diffs are the gradients")

- **URL**: https://github.com/Birfy/agentdescent (MIT, Python, 191 stars at this read; `agentdescent` 0.5.1 on PyPI; docs at https://birfy.github.io/agentdescent/)
- **Date**: 2026-10-15 (daily X intake)
- **Source / Poster**: @DanKornas, https://x.com/DanKornas/status/2110811525036245166
- **Summary / Key Claims** (upstream README and `agentdescent --help`): treats an agent artifact (a skill folder, a prompt, a harness, code) as the parameters of an optimizer. Several workers run tasks from a `cases.jsonl` in parallel and asynchronously, each proposes a diff to the artifact, and an aggregator merges the diffs into one version-controlled ledger: edits on disjoint keys fuse, edits on the same key conflict and get a three-way merge. A reflector and a scorer turn task outcomes into the next round's edits, and a held-out split checks the result. The CLI covers `init` (starter spec for a path), `plan` (validate and estimate cost, runs nothing), `evolve`, `status`/`watch`, `show` (diff against the original), `apply` (writes back, backing up first), `cancel`/`resume`, `doctor`, and an MCP server. Agents can be `openai_compatible(...)` (any base URL, including a local vLLM or llama-server), Claude, or an agent CLI (Claude Code, Codex, OpenCode).
- **Why it matters here**: this is the self-improvement loop pfy-mentat wants, aimed at the thing we actually change most: `SKILL.md` folders and prompts. Today skills are edited by hand or by one Build run, and the toolsets drop-in (`docs/build-dropins/pfy-mentat-toolsets.md`, step 2b) plans DSPy for prompt tuning. AgentDescent works on a whole skill directory, keeps every round in a ledger, and only writes back on `apply`. With `openai_compatible` pointed at Ollama or llama-server on nimo it needs no paid key.
- **Fit on nimo**: Yes. Pure Python (3.9+, NumPy) in a venv under `~/DEVELOP/pfy-mentat/tmp/agentdescent/`. Real runs need a model: a local OpenAI-compatible endpoint on nimo (for example `qwen3.6:35b`, the current decision-benchmark pick) or OpenCode on a local model. Set `--store` (or `$AGENTDESCENT_HOME`) under `tmp/`, because the default run store is `~/.agentdescent/runs` (nimo layout lock).
- **Verified on the Grok Bot box** (venv in `/tmp`, bubblewrap read-only root, no network, temp HOME): `agentdescent demo` built its CSV-total skill, ran 12 tasks over 4 rounds x 2 workers with its offline local agent, reported `held-out reward: 1.000`, learned `rules.md -> 'COLUMN: amount'` from the wrong `'COLUMN: id'`, and left the skill on disk unchanged. The temp HOME stayed empty. `doctor` lists which agent CLIs and provider keys it can see.
- **Finding**: the default run store is in the real HOME, and `doctor` reports provider keys present in the environment, so trials should run with a clean env (the smoke uses `run_isolated`) and `--store` under `tmp/`. The demo's agent is a local program, so the demo proves the loop, not model quality.

- **How this fails / how we recover**:

| Risk | How it fails | Recovery |
|------|----------------|----------|
| Run store lands in the real HOME on nimo | `~/.agentdescent/runs` appears outside DEVELOP | Always pass `--store` (or `$AGENTDESCENT_HOME`) under `tmp/`; the smoke snapshots the real `~/.agentdescent` before the run and compares it after (also on timeout), recording `real_home_untouched`; it also checks the temp HOME stays empty |
| An evolved skill overfits the cases | Held-out reward looks good, real use gets worse | Keep a held-out split; review `show` diffs; `apply` only through a normal PR with Tester and Reviewer |
| Agent CLI worker writes outside its sandbox | A Claude Code or Codex worker edits the repo | Use `openai_compatible` against a local endpoint first; run CLI workers only in a throwaway worktree |
| Local model too weak as reflector | Rounds commit nothing | Record it as the eval result; try a bigger local model before any paid one |
